# 架构说明

本文档描述 My MC v2 的模块划分、依赖规则与关键设计决策。目标是让多个开发者（或
多个 Agent）可以**并行修改不同模块而不互相破坏**。

---

## II. 关键设计决策

### 1. 数据与控制分离：Chunk 存 TypedArray，不存对象

区块方块数据存放在扁平 `Uint8Array` 中，索引为 `y * size² + z * size + x`。

- **为什么**：一个 16³ 区块有 4096 个方块，32×32 的加载范围有 100 万+ 方块。用对象
  表示会产生同等数量的堆分配，GC 停顿会直接表现为掉帧。
- **代价**：失去按方块附加任意字段的能力；需要额外结构（例如区块内的
  `Set<BlockPosition>`）来表达"被修改过的方块"这类稀疏信息。

坐标转换集中在 `world/coords.ts`，**所有**模块都必须通过它换算
世界坐标 ↔ 区块坐标 ↔ 区块内局部坐标，禁止各自手写位运算。

### 2. 渲染：面剔除 + 贪心合并，一个区块少数几个 Mesh

- **为什么**：一个方块一个 Mesh 的实现在 32×32 区块下需要数百万次 Draw Call。
- **做法**：只生成与空气/透明方块相邻的面（面剔除），再在同一平面上合并共面矩形
  （贪心合并），输出单个 `BufferGeometry`，按材质（不透明/透明/水）分包。
- **注意**：贪心合并以**面方向**为单位，因此不透明与透明方块必须分到不同 Mesh，
  否则透明排序会出错。

### 3. 世界分块与流式加载

- Chunk 按需生成、按渲染距离卸载；修改过的区块才写盘。
- 世界生成与网格构建在 **Web Worker** 中完成，主线程只做 `BufferGeometry` 上传。
- **为什么**：地形生成包含多层 FBM 噪声，主线程执行会造成可感知的卡顿。

### 4. 地形确定性优先于"更聪明的噪声"

自研噪声实现而非引入 `simplex-noise`：

- **为什么**：存档只保存种子与**被修改的方块**，未修改区块在加载时重新生成。如果
  依赖库改变了噪声实现，玩家回到旧世界会发现地形变了。确定性属于存档格式的一部分。

### 5. 固定时间步物理 + 渲染插值

`engine/core/GameLoop` 以固定 1/60 秒推进模拟，渲染时给出插值系数。

- **为什么**：AABB 逐轴推进的碰撞求解对 delta 敏感，变步长会让玩家在低帧率下穿墙。
- **保护**：单帧最多追赶 `maxSubSteps` 步，超出部分丢弃并计入
  `droppedSeconds`，避免"死亡螺旋"。

### 6. UI 使用原生 DOM，而不是前端框架

- **为什么**：HUD 每帧只更新文本与少量类名，框架的 diff 与订阅机制在这个场景下是
  纯开销；更重要的是，框架会把游戏状态拖进响应式依赖图，让引擎模块无法脱离
  DOM 测试。
- **约束**：`ui/` 只读上层传来的**快照数据**，不持有引擎对象的引用。

## III. 模块契约（并行开发的边界）

> 每个模块只通过下列接口被外部使用。**修改接口必须同步更新消费方**，这是并行开发
> 不互相破坏的前提。

| 模块                       | 对外接口                                                                       | 说明                                          |
| -------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------- |
| `engine/core/GameLoop`     | `new GameLoop(callbacks, options)`、`start/stop/advance`、`metrics`            | 固定步长，注入 `FrameScheduler` 以便测试      |
| `engine/core/FrameStats`   | `record(frameTimeMs)`、`snapshot()`                                            | 环形缓冲，记录时不分配内存                    |
| `rendering/capabilities`   | `detectGraphicsBackend(canvas)`                                                | **必须传入一次性 canvas**，探测会销毁上下文   |
| `rendering/createRenderer` | `createRenderer(canvas, options)` → `{ renderer, dispose }`                    | 唯一创建 `WebGLRenderer` 的位置               |
| `rendering/Environment`    | `createEnvironment(scene, options)` → `{ hemisphereLight, sunLight, dispose }` | 昼夜系统通过操作 `sunLight` 驱动              |
| `ui/BootOverlay`           | `showLoading/setProgress/showFatal/hide/dispose`                               | 接管 `index.html` 中的静态首屏                |
| `debug/DebugOverlay`       | `new DebugOverlay(root, { rows })`、`set/setNumber/toggle`                     | 行键固定，未知键被忽略                        |
| `utils/errors`             | `AppError`、`toAppError`                                                       | `code` 供恢复逻辑分支，`userMessage` 面向玩家 |

## IV. 测试策略

| 层级 | 运行环境                 | 验证内容                                           |
| ---- | ------------------------ | -------------------------------------------------- |
| 单元 | Node / jsdom             | 纯逻辑：数学、噪声、区块索引、背包规则、存档序列化 |
| 集成 | jsdom                    | 模块协作：场景装配、渲染器工厂、UI 与状态交互      |
| E2E  | 真实 Chromium + 生产构建 | 启动、输入、交互、存档往返                         |
| 视觉 | E2E 内解码 PNG           | 非黑屏、区域色调、UI 不被裁切、Z-fighting/闪烁回归 |

**为什么 E2E 跑生产构建而不是开发服务器**：只有生产产物会暴露 hash 资源名、
代码分割与压缩引入的问题。Playwright 的 `webServer` 因此指向 `vite preview`。

## V. 扩展新模块时的检查清单

1. 放进哪个顶层目录？需要新增层级吗（同步改 `architecture.test.ts`）？
2. 它依赖谁、被谁依赖？是否引入循环？
3. 它需要 `dispose()` 吗？谁调用？
4. 纯逻辑部分能否脱离 DOM/WebGL 测试？
5. 需要新的调试指标吗？加到 `DebugOverlay` 的行清单。
6. 需要新的存档字段吗？写上版本号与迁移函数。
